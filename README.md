# The Hollow Warden

Public source: [openifsoul/example-dungeon](https://github.com/openifsoul/example-dungeon).

Independent original browser host, extracted from the IfSoul demonstration. This
repository owns the game and its adapter; it is not part of a central game catalog
implementation. Engine: phaser. Source and vector assets
are Apache-2.0; adapted shadcn Button retains its MIT notice in LICENSES.

## Run independently

Use Node 22.18–24 and pnpm 10.15.0. The included vendor SDK tarball is an explicit
unpublished development dependency, referenced by relative path and locked. No
Core checkout, account, provider key or registry-published IfSoul version is needed.

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm dev
```

Open the printed loopback URL. Scenario mode is deterministic and makes no remote
calls. Pause/resume and restart are in the standalone panel; game-specific controls
remain inside the playfield. Unavailable optional inference falls back visibly.
Build output web-dist is standalone; dist contains package exports.

## Host integration

`@ifsoul/example-dungeon` exports `mount(container, options)` with SDK
GameMountOptions/MountedGame. Import `./simulation` for independent game rules;
`./adapter` exports createExampleSession (pause/resume/destroy plus bounded chat) for the same SDK bridge lifecycle used
by the standalone panel. All mechanics remain in src/game. The adapter handles
bounded proposals/dialogue and reports, never locomotion or gameplay controllers.
Destroy or abort owns cleanup, including late mount completion.

A consuming application supplies its own trusted bridge/transport and authentication.
The standalone optional connection uses SDK HTTP transport at the same-origin
/api/demo/bridge endpoint. For local development only, set IFSOUL_API_ORIGIN to
an explicit HTTP loopback IfSoul origin before pnpm dev, then select Local IfSoul
proxy. The development server validates the target and rewrites Host/Origin
server-side. This connection needs the separately running trusted local IfSoul
runtime. No Clerk token or provider key is accepted by this example.
Cloud Playground consumes the exported mount inside its own authenticated origin;
standalone cloud authentication and cross-origin hosting are not implemented.

## Package without publication

Run pnpm build then pnpm pack --pack-destination output/packages. The SDK is bundled
inside the package tarball so another project can install the example tarball
without unpublished registry access. vendor/ifsoul-adapter-sdk-0.3.0.tgz
is regenerated by the SDK owner from its independently packaged SDK, then copied
here explicitly; do not replace it with an absolute file dependency.

Simulation and adapter lifecycle tests run with pnpm test. Browser checks are
separate and headless. The owner authorized manual public GitHub source release. No npm publication,
deployment or production support is claimed by this example.
GitHub Actions PR/push checks and local release boundaries are described in the
[execution policy](docs/deployment.md).

## Game controls and limits

Choose Tank or Healer; the companion takes the complementary role. Move with WASD/arrows or touch controls, hold Space/Attack, and use Shift/Ability for guard or nearby healing. Clear three rooms and the Warden. Four optional speech requests never control combat, movement or the host companion AI.

Role selection is reported as a completed player choice observed by the companion,
with both historical roles in the source text. Room and expedition resolutions
remain host outcomes. A player Healer's ability records help only when it actually
increases the nearby companion's health; self-healing, full health, out-of-range
casts and cooldown attempts do not count. Each room emits at most one aggregated
help outcome on clear or loss, preserving user actor, user observer and agent
recipient. No per-frame model calls or gameplay rules are added.

The simulation test `fixture combat damage and healing` demonstrates two distinct
room help outcomes using explicitly arranged near-expiry enemy strikes, then the
ordinary healing ability and room resolution. Run `pnpm exec tsx --test
--test-name-pattern='fixture combat damage and healing' tests/simulation.test.ts`.
This is controlled simulation evidence, not proof of a natural player route:
the current companion can evade all damage in deterministic expedition play,
and a normal-game sequence producing two help outcomes has not been verified.

The local .npmrc selects hoisted installation because pnpm bundling requires it.
No dependencies resolve through a sibling checkout. The included SDK tarball is
redistributed under its Apache-2.0 license, with its own bundled notices.

The adjacent chat uses the same adapter bridge and bounded session history as the
game, including host observations and prior user/agent messages. Messages accept
1–600 characters. Scenario and fallback replies retain their provenance labels.
Destroy aborts local chat delivery; it does not claim upstream inference cancellation.

## Portable declarations and validation

Package declarations support strict TypeScript NodeNext consumers without Vite
ambient types or skipLibCheck. After TypeScript emits declarations, the local
build script removes only side-effect CSS imports from .d.ts files. It leaves
JavaScript and stylesheet assets intact. Friendly 21 and Dungeon consumers must
explicitly import the package's `style.css` export in their browser composition.
The standalone entry already includes its game's styles through the game module.

Independent validation used source copies outside the Core checkout, including
the supplied vendor tarball and lockfile, followed by frozen installation and
checks. These were filesystem copies, not clones of a committed repository.

## Original sprite art

The game uses a hand-painted [sprite set](art/README.md): three persistent
companion identities in both roles, neutral player bodies, three enemies and
dungeon props. The prepared atlas and floor are embedded through the package's
public build; no sibling checkout, image provider or runtime art request is needed.
Vitals and room status sit inside the arena; there is no duplicate title above it.

## In-game speech

The host owns its speech bubble, placement and animation. It implements the
optional `MountedGame.say(speech)` presentation API for player-requested chat.
Autonomous/requested game dialogue is displayed after the game's normal freshness
checks. Bubbles type the text visually, announce the whole line accessibly, respect
reduced motion and release timers/animations on pause or destruction. The SDK
returns authored scenario/fallback reactions instead of quoting raw host reports;
model plan explanations are not dialogue. No action authority is added.

Host-requested decisions and remarks await the SDK bridge's configured bounded
request deadline. The game does not impose a shorter model-independent timeout
that could discard a valid slower reply. Rejected requests retain the existing
labelled host fallback/unavailable state, and phase/version, pause and destruction
checks still prevent stale adoption or late presentation. A custom injected
`GameBridge` must provide bounded settlement and honor its connection lifetime;
an indefinitely pending custom bridge is not a supported integration.
